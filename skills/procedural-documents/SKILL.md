# 程序性文书系列（procedural-documents）· 路由中枢

> 民商事诉讼"程序性文书"统一起草入口。多数程序性文书骨架相同（标题→受文法院→当事人→请求事项→事实和理由→此致→落款→附件），差异集中在请求事项与法律依据。本技能负责**识别文书类型 → 加载对应家族子规范 → 按规范起草**，把上下文占用控制在"路由表 + 单个家族文件"。

---

## 0 | 工作原则（务必先读）

1. **不要把八个家族文件一次性全读进来。** 先用第 2 节路由表判定属于哪个家族，再 `Read` 该家族对应的 `references/0X-*.md` 单个文件，连同 `references/00-通用规范.md` 一起执行。
2. **法条必须现行有效且经核验。** 本系列内嵌的条文号以"民诉法 2023 修正（2024-01-01 施行）/ 民诉法解释 法释〔2022〕11 号"为准。写入正式文书前，按 `00-通用规范.md` 的"法条核验闸门"用法律检索后端（元典/北大法宝，运行时自动适配+灾备，见 profile.md「外部能力后端」）的 `LAW.statute_detail`/`LAW.article_detail` 复核条文号与原文，校验不可用时标注「[L4-法条待验证]」。
3. **第八家族不是填空题。** 实现担保物权、撤销仲裁裁决、第三人撤销之诉、执行异议之诉具有较高论证深度，须充分收集材料、深度调用法律检索后端（法条+案例），实体论证要充分，参见 `references/08-其他程序类.md`。
4. **管辖权异议已完整并入本系列。** 路由到第二家族时，直接加载 `references/02-管辖权异议.md` 起草（含材料解析、工商信息核验、管辖规则分析、法条校验、撰写、Word 输出全流程），不再转交外部技能。
5. **输出为可提交法院的 Word 文书**（经 `Word 转换后端`（DOCX.md_to_docx） 生成），保存到输出目录并回链。
6. **输出前必过 `/legal-verification` 闸门。** 生成 Word 前，先调用 `/legal-verification` 对全文法规/法条/案例引用逐条核验，判定全为「准确/准确(有省略)」才放行；出现「时效风险/语义不一致/未命中」须修正后重新核验。法律检索后端不可用时按降级标注「[L4-法条待验证]」并提示人工复核，不得静默跳过。

## MCP 预检

执行前调用 `MCP.list_tools` 探测以下后端是否可用：
- 法律检索：关键词匹配 `law`/`yuandian`/`pkulaw`/`法宝` → 映射 LAW.* 能力
- 工商信息：关键词匹配 `qcc`/`企查查`/`天眼查`/`biz` → 映射 BIZ.* 能力

**探测结果处理**：
1. **全部可用** → 静默进入工作流。
2. **部分不可用** → 用 `AskUserQuestion` 告知用户："检测到{不可用后端名}尚未连接。{该后端的作用}。建议前往宿主平台的连接器/MCP 设置（Agent 运行时 / Claude Code / Cursor / Gemini CLI / OpenCode 等） 中配置。是否暂不配置、以降级模式继续？"
   - 用户选择配置 → 等待配置完成后重新执行
   - 用户选择继续 → 降级执行，对应位置标注 L4 标签
3. **全部不可用** → 同上询问，降级标注 `[L4-法条待验证]`/`[L4-主体信息待验证]` 等。

> 探测协议与降级规则详见 Expert.md「MCP 预检协议」。

### 2.1 易混淆消歧

- "解除保全" → ③；"撤回保全申请" 属于撤回行为，亦在 ③ 处理。
- **仲裁保全**：仲裁财产保全申请书致送仲裁委员会（由仲裁委转交法院执行），归 ③。"诉前/仲裁前保全"致送有管辖权的法院，同归 ③。
- "证人出庭" → ⑤（非 ⑥）；"专家辅助人/有专门知识的人出庭" → ⑥（与鉴定同组，因其针对鉴定意见与专业问题）。
- "委托书/身份证明" → ①；本家族提供**通用空白范本与填写规则**。
- "执行异议"（对执行行为/执行标的，向执行法院提，裁定式）→ ⑦；"执行异议之诉"（异议被裁定驳回后另行起诉，判决式）→ ⑧。
- "撤销仲裁裁决" vs "不予执行仲裁裁决"：前者向仲裁委所在地中院申请（⑧）；后者在执行阶段提出（执行抗辩，归 ⑦，并在 ⑧ 交叉指引）。
- **仲裁管辖权异议**：由被申请人向仲裁委员会提出（请求驳回申请人仲裁申请），归 ②；与法院管辖权异议共用家族，但致送对象和法律依据不同（仲裁法第20条）。
- **增加/变更/放弃仲裁请求**：归 ④，结构同诉讼版，致送改为仲裁委员会。

### 第零步：主体信息自动补充（文书生成前必经）

所有诉讼文书在生成最终稿之前，必须完成主体信息的核实与补充：

1. **企业主体**（公司、合伙企业、非法人组织等）：
   - 调用工商信息能力槽（BIZ.company_info 或同等接口，如企查查MCP `get_company_registration_info`）查询最新工商登记信息
   - 补充字段：企业全称、统一社会信用代码、住所地、法定代表人/负责人
   - 禁止在诉讼文书主体信息中写入：企业类型、成立日期、注册资本、经营范围等工商登记冗余信息
   - 若能力槽不可用，但用户提供的案件材料中包含相关信息，直接从材料提取并补充
   - 若材料中亦无相关信息，主动向用户询问："请提供[企业名称]的统一社会信用代码、住所地、法定代表人信息"
   - **用户明确拒绝提供时，保留"[待用户补充]"占位符，严禁自行编造或填写虚假信息**

2. **自然人主体**：
   - 无MCP可用，仅依赖用户提供的材料或用户补充
   - 从案件材料中提取：姓名、性别、出生日期、身份证号码、住所地/经常居住地
   - 材料中缺失的，主动向用户询问
   - **用户拒绝提供时，保留"[待用户补充]"占位符，严禁编造**

3. **适用文书类型**：
   - 起诉状、答辩状、代理词中的当事人信息部分
   - 证据目录中的主体证据组
   - 程序性文书中的申请人/被申请人信息
   - 案件事实梳理中的主体识别部分

## 3 | 标准执行流程

```
用户请求
  → 第2节路由判定家族（必要时1问澄清）
  → Read references/00-通用规范.md（共用：信息清单/称谓/法条核验闸门/输出规范）
  → Read references/0X-该家族.md（该家族专属：子文书清单/请求事项写法/专属要件/法律依据/附件）
  → 收集案件信息（缺则按清单提问；可读取已上传材料/案件工作空间）
  → 法条核验闸门：法律检索后端复核条文号与原文（不可用标[L4-法条待验证]；第七家族另需案例检索）
  → 起草（套用骨架 + 家族专属请求事项与事实理由）
  → ⛔ 输出前必过闸门：调用 /legal-verification 逐条核验全文法规/法条/案例引用，判定全为「准确」才放行（不可用按降级标[L4-法条待验证]并提示人工复核）
  → 🔗 台账自动回写（强制，无需用户触发）：
    调用 /case-manager §0.7 自动同步接口：
    1. 用案件简称/案号搜索台账 recordId
    2. 读取「案件进展」字段（profile.md ledger_fields 映射）原值，追加："{YYYY.M.DD} {文书类型}已起草（核心论点：{1句}），Word已生成"
    3. 更新「下一步动作」字段（profile.md ledger_fields 映射）= "{下一步建议动作}"
    4. update_records 写入
    5. 搜索无结果 → 跳过回写，输出末尾标注"⚠️ 本案尚未建档"
    6. 回写失败 → 不阻塞，标注"⚠️ 台账未自动更新"
  → Word 转换后端（DOCX.md_to_docx） 生成 → 保存输出目录 → 回链 + 提交提示（份数、签章、附件、期限）

> **🔒 Word 排版铁律（强制）**：所有诉讼文书转 Word 时，**必须**使用 `scripts/md2docx_legal.py` 转换脚本（路径：`${SUITE_ROOT}/scripts/md2docx_legal.py`），用法：`python3 md2docx_legal.py input.md output.docx`。该脚本严格按照最高人民法院诉讼文书样式模版执行排版：宋体、标题二号居中不加粗、正文四号首行缩进2字符、行距固定25磅、此致缩进+法院顶格+签名右对齐+附件缩进。**禁止**使用 pandoc 或其他工具直接转换（格式不达标）。排版铁律全文见 `format-spec.md`。
```

## 5 | 执行规则

1. **路由克制**：1–2 轮内完成家族判定，不过度追问。
2. **按需加载**：只读取命中的家族文件 + 通用规范，严禁全量读取。
3. **核验前置**：任何写入文书的法条，先过核验闸门；校验不可用标「[L4-法条待验证]」。
4. **不杜撰**：缺失的案件信息向用户索取，不臆造当事人、案号、金额、财产信息。
5. **文件安全**：改写用户已有文书前先备份；最终成果输出到输出目录并回链。
